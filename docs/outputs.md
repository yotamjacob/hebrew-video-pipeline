# Outputs: history, downloads, retention, scheduling, cost

Deep contracts moved out of CLAUDE.md (2026-08-09) to keep the always-loaded core lean.
**Read this file fully before changing** job history/retention, re-edit, downloads (web+native), SRT, the preview player source, backups, cost tracking, or Metricool scheduling. Everything here is load-bearing;
update it in place when behavior changes.

**Job history & retention** — every successful `burn_captions_fn` records `{name, ts, size, duration}` in the `hebpipe-jobs` modal.Dict (key = `…_out.mp4` output key) and runs `prune_volume()`. **`process_video` also records the job for a terminal cut-only result** (`not captions_list and not transcribe_for_broll` — the site sends the user straight to download/schedule and no burn follows), keyed by its `…_cut.mp4` key, so silence-only videos are retained, appear in History, and are schedulable exactly like burns. Caption/B-roll jobs skip this (their burn records the `_out.mp4`). Retention: outputs recorded in `jobs_store` (burned `_out.mp4` or terminal `_cut.mp4`) deleted after `JOB_RETENTION_DAYS` (30); scratch files (`_src.mp4`, unrecorded intermediate `_cut.mp4`, chunks) after `SCRATCH_RETENTION_HOURS` (48) — a `_cut.mp4` present in `jobs_store` is in `protected` and survives the scratch sweep. Nothing else deletes volume files — the old delete-on-download and delete-after-schedule behaviors are gone. History tab uses `GET /jobs`, `DELETE /jobs/{key}` and the existing `/thumbnail/` + `/download/` routes — **both `/jobs` list and DELETE accept `_out.mp4` AND `_cut.mp4` keys** (cut-only results were previously recorded+retained but hidden from History because the list filtered to `_out.mp4` only). `/thumbnail` caches its JPEG as `<key>.jpg` on the volume (first hit ~5 s ffmpeg, then instant); `prune_volume` keeps the `.jpg` while its video is protected and deletes them together. **Prune fail-safe:** the scratch sweep is skipped if `jobs_store` is empty while output videos still exist on the volume — a blanked/lost Dict can no longer mass-delete every output past 48h. **Re-editable jobs also pin their source:** a burn record's `edit.src_key` (and any `edit.broll[].video_key`) is added to `protected`, so the cut it burns onto outlives the 48h scratch window (see the re-edit note below).

**Re-edit a previous export (2026-07-27)** — History rows offer an "edit again" pencil that reopens the editor on a finished burn instead of forcing a re-upload. Captions are baked into the output permanently, so the re-burn targets the ORIGINAL cut: `burn_captions_fn` records everything needed as `edit` on the job record (`src_key`, captions, hook, broll, font, font_size, margin_v_pct, caption_style) via `_record_job(..., edit_state=…)`, and `prune_volume` pins `src_key` + cached `broll_*.mp4` for the job's 30-day life (they were 48h scratch — the feature is dead without this pin; tripwire: `tests/backend/test_history_edit.py`). `GET /jobs/{key}/edit` serves that state (checks `_owned_key` on BOTH the job and its `src_key`, and 410s `source_gone` if the cut is really gone); `/jobs` list carries `editable: bool(meta.get("edit"))` so pre-feature jobs simply show no button. Frontend `editFromHistory()` mirrors the reload-resume rehydration (`captionsData`/`videoKey`/font/size/margin + `_applyCaptionStyleValues`/`_restoreHookState`/`stockBrollSelections`), sets `hasBurnedOnce` so the CTA reads "re-burn", and shows `#historyEditHint`. Two gotchas: the size and hook-scale controls are `<select>`s of discrete steps, so a stored value with no matching `<option>` must be snapped via `_snapSizeOption` (a raw assignment blanks the control and silently desyncs it from what burns); and only the CHOSEN hook is stored, so `_restoreHookState` rebuilds a ONE-option list and must run AFTER `showCaptionEditor()` (which clears hook UI). B-roll candidate cards aren't stored — the tab shows a kept-count note (`stock.keptFromExport`) and a fresh search replaces the picks. A re-burn is quota-free (credits are spent at `/process` spawn) and creates a NEW History entry; the original stays. `burn_captions_fn` also now falls back to a B-roll item's `download_url` when its cached clip is missing instead of dropping the insert. Tests: `tests/backend/test_history_edit.py`, `tests/frontend/history_edit.spec.js`.

**Device download is browser-native, via a hidden iframe (2026-07-11)** — the finished video/audio is NOT fetched into a JS Blob anymore (that was a single-stream, RAM-buffered, no-progress transfer that felt slower than the 6-way-parallel upload, and it gated the success banner). `_browserDownload(url)` sets the `src` of a reused hidden `#_dlFrame` iframe to `_withToken('/download/<key>/?filename=…')`; the server's `Content-Disposition: attachment` makes the browser stream it to disk (native progress shelf). **Why an iframe, NOT an `<a>`/`location`:** the API is cross-origin (`modal.run`), so the anchor `download` attr is ignored and a plain click/navigation is treated as a TOP-LEVEL navigation — which fires the `beforeunload` "leave page?" prompt BEFORE the server's Content-Disposition can turn it into a download, and cancels the download if the user dismisses the prompt (this actually shipped briefly and broke downloads). An iframe navigation never unloads the top page → no prompt. The server sets the filename from the `filename` query param, so the client needs no `download` attr. Auth rides in `?token=` (media token, computed at call time so it's fresh; the backend also accepts the session token via `?token=` on GET). `resultDownloadUrl` holds the URL (reset with `resultBlob`); it is **deliberately NOT a `beforeunload` trigger** (the file persists server-side 30 days + in History, so leaving loses nothing, and the download must never provoke the prompt). `triggerDownload()` prefers it, keeping the old Blob path as fallback. Both burn paths, cut-only (`_finalizeAndDownload`) + `downloadAudio` use it, and the burn success banner + celebration + pipeline-unlock fire IMMEDIATELY on burn completion (no await on the transfer) — scheduling was always independent (server-side `/media/` URL). Backend `/download` uses a 1 MB chunk for full (200) replies vs 256 KB for range (206) preview seeks. The preview player still fetches its own Blob (`_previewObjURL`) for smooth scrubbing — unrelated. Tests: `tests/frontend/action_lock.spec.js` (immediate banner + hidden-iframe regression guard), `celebrate.spec.js`.

**Metadata backup (R2/B2)** — the critical Dicts are the only non-reconstructable state and have no native Modal backup. `backup_dicts` (`pipeline_fns.py`, scheduled daily) snapshots `hebpipe-jobs`/`hebpipe-users`/`hebpipe-quota`/`hebpipe-purchases`/`metricool-oauth` to one JSON file and uploads it to an S3-compatible bucket, keeping the 30 most recent. `restore_dicts` merges a snapshot back into the live Dicts (dry-run by default; `modal run app_modal.py::restore_dicts --key backups/… --which users --apply`). Both are imported into `app_modal.py` so `modal run` can address them. Creds come from the `hebpipe-backup` secret (`S3_ENDPOINT_URL`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_REGION=auto`); best-effort — missing creds just log + skip, so a deploy without them never fails. Videos are NOT backed up (30-day retention by design). The snapshot holds password hashes + OAuth tokens, so the bucket MUST be private.

**AI token spend + Costs tab (2026-08-09)** — per-video compute alone understated true cost: AI calls (hooks, B-roll, proofread, post captions) bill separately and aren't tied to a video key. `_record_ai_spend(costs_store, kind, model, usage)` (pipeline_core, best-effort, never raises) writes an `ai:{ms}:{kind}` ledger entry per Anthropic call with token counts + USD at list rates (`AI_USD_PER_MTOK`, prefix-matched by model family; cache reads 0.1x, writes 1.25x input). Wired at EVERY call site: proofread (pipeline_fns), hook + post_caption (content_fns), broll_moments + broll_context (broll_fns), broll_vision (BOTH `score_clips` call sites via the `on_usage` callback — stock_helpers stays pure, no Modal imports) (keywords was wired too until the feature was removed 2026-08-09). `_cost_summary` aggregates `ai:` keys separately (never as "videos"): `ai_usd`, `ai_calls`, `ai_tokens`, `ai_by_kind`, and the pricing-decision figures `all_usd`/`all_per_video` (compute + AI per delivered video). Records prune with the normal `COST_RETENTION_DAYS` sweep (it iterates all costs_store entries by ts). The UI is now its own admin-only **Costs tab** (`#tabCosts`/`#costsView`, gating + saved-tab restore identical to Admin's; the Admin tab keeps user limits only): all-in hero, compute/AI/GPU stats, per-mode table, AI-by-feature table ranked by spend. Tripwires: `test_every_ai_call_site_is_metered` in `tests/backend/test_cost_tracking.py`; UI in the Costs cases of `quota.spec.js`.

**Per-job compute cost (2026-07-31)** — a credit is sold per VIDEO while the compute behind one varies ~40x with length and ~20x with the 4K upscale, so margin was estimated, never measured. `process_video` now writes `{ts, uid, dur, enhance, audio, gpu_secs, steps}` to the `hebpipe-costs` Dict keyed by its cut key, and `burn_captions_fn` writes `{ts, uid, burn_secs, broll}` keyed by its output key (a re-burn is quota-free but not compute-free, so it lands as its own entry). `_cost_summary(costs_store, since)` in `pipeline_core.py` aggregates a window into totals, `usd_per_video` and a per-enhance-mode breakdown with `gpu_per_src` (GPU seconds per second of source) — the figure that says whether a length-based credit rule is needed. Surfaced by `GET /admin/costs?days=7` (admin-only) and folded into the `daily_usage_report` digest. Rates are Modal list prices in `pipeline_core.py` (`GPU_USD_PER_SEC`, `CPU_USD_PER_SEC`); they exclude container startup/idle, so the output is a floor for comparing jobs, not an invoice. Records outlive their videos (`COST_RETENTION_DAYS = 90` vs 30 for outputs) because pricing is judged over months; pruned by `prune_volume`. Included in the metadata backup. Surfaced in the app as a card at the top of the **Admin tab** (`#costBody`, `loadCosts()` — fired from `loadAdmin()`), with a 7/30/90-day range switch: a hero cost-per-video figure, videos/total/GPU-time stats and a per-mode table. Deliberately NOT a chart — it is a handful of aggregates, so the figures wear plain text tokens and carry no series colour. Tests: `tests/backend/test_cost_tracking.py`, the admin-cost cases in `tests/frontend/quota.spec.js`.

**Download toast opens the VIDEO, not a folder (2026-08-09, needs the NEXT binary)** — `NativeDownloaderPlugin.openFile({id, mimeType})` resolves the finished download via `DownloadManager.getUriForDownloadedFile` (content:// only when SUCCESSFUL — an in-flight/failed download falls back to `openDownloads`, never ACTION_VIEW on a half-written file) and fires ACTION_VIEW. The JS toast action prefers `openFile` (label `download.openVideo`) when the shell has it, else keeps the openDownloads folder action; the legacy Filesystem path keeps the Share-sheet fallback (no launcher bridge exists in old shells - field report: the filename link "opened the sharing modal").

**Native finished-video downloads use Android DownloadManager (2026-07-29)** — `_browserDownload` must prefer the custom `NativeDownloader` Capacitor bridge. It enqueues the authenticated URL in Android's system `DownloadManager`, saves into public `Downloads`, and leaves progress plus the completed file in the notification shade. `openDownloads()` backs the folder buttons shown under both finished-video download buttons. Keep the media token in the URL and never buffer large final videos into a WebView Blob. `Filesystem.downloadFile` into public `Documents` remains compatibility-only for installed native shells that predate the bridge; the new behavior therefore requires an updated Android binary, not only a web deployment. A hidden cross-origin iframe remains the browser path. History downloads use the same helper. Regression tests: native cases in `tests/frontend/share.spec.js`.

**SRT download is local, so it takes neither path (2026-07-31)** — `downloadSRT` builds the file in the page, and `DownloadManager` can only fetch an http(s) URL, so the video helpers don't apply. On native, `_nativeSaveSrt` writes the text to `Filesystem` `CACHE` and opens the `Share` sheet (a `blob:` `<a download>` is a SILENT no-op in the Android WebView — this was the "SRT download does nothing on mobile" report); both plugins already ship in the installed binary, so this is a web-only deploy. It returns `false` on a shell without them and falls through to the browser path. The browser path now **appends the anchor to the DOM** before clicking and revokes the object URL on a 10s timer — a detached anchor is ignored by mobile browsers, and a same-tick `revokeObjectURL` cancels the download before it starts. Tests: `tests/frontend/srt.spec.js`.

**Preview player is STREAM-FIRST with a blob upgrade (2026-07-16)** — the editor preview no longer waits for the whole cut video to download into a Blob (a 9-min CRF-18 cut is hundreds of MB → minutes of spinner on mobile; field report). `_ensurePreviewReady` (the checklist "Loading preview" step) now grants the prefetch only a **2.5s grace** (`__PREVIEW_READY_WAIT_MS` seam) — small clips still land the blob inside it and open on the instant in-memory copy. The player setup waits 1.5s (`__PREVIEW_BLOB_WAIT_MS`), then sets the `<video>` src to the token'd `/download/<key>` URL — the backend's 206 byte-range support makes it play within seconds — and calls `_armPreviewBlobUpgrade(vid)`: when the background `_prefetchPreviewBlob` promise resolves, the blob is probed (`_probeVideoURL`) and hot-swapped in at the next PAUSED moment (playhead restored via one-shot `loadedmetadata`; guards: `_playerSetupDone`, same `videoKey`, src not already blob) so scrubbing turns zero-latency without ever interrupting playback. The prefetch keeps running regardless because the native share warm-up reuses its blob. Tests: `tests/frontend/player_recovery.spec.js` ("long video: player streams within seconds…").

**Metricool is per-user** — tokens are namespaced `tokens:{uid}` in the `metricool-oauth` Dict; the PKCE state entry carries `{verifier, uid}` so the public `/oauth/callback` attributes the connection. Each user's brand/blog id is discovered lazily in `schedule_post_fn` via MCP `tools/list` (tool name matched by containing "brand"/"blog", not hardcoded) and cached on the token record — **never** falls back to a shared brand (`no_brand` error instead). `_mcp_open`/`_mcp_parse` are the shared MCP handshake. NOTE: brand auto-discovery is unverified against the live Metricool MCP — confirm with a real connected account.
