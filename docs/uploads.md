# Uploads & network resilience

Deep contracts moved out of CLAUDE.md (2026-08-09) to keep the always-loaded core lean.
**Read this file fully before changing** chunked/R2/native uploads, resume/reconcile, or the deferred spawn. Everything here is load-bearing;
update it in place when behavior changes.

**Mobile upload resilience (design, 2026-07-05)** - chunk POSTs use **XHR, not fetch** (`_postChunkBytes`): fetch reports no upload progress (bar frozen at 0% until a whole 5 MB chunk lands) and has no timeout (a stalled connection hangs forever). XHR gives byte-level `upload.onprogress` (summed across concurrent chunks via `loadedByChunk[]`) and a **stall watchdog** - abort+retry only when NO bytes move for `CHUNK_STALL_MS` (20 s; overridable via `window.__CHUNK_STALL_MS` for tests), so a slow-but-moving upload is never killed, only a truly dead one. Retry policy: a chunk gives up only after 6 network failures **that happen while the page is VISIBLE** - failures coinciding with backgrounding (the OS killing in-flight XHRs) are detected via a `_hiddenEpoch` counter (bumped on every `visibilitychange`-to-hidden; captured before send, compared at failure) and do NOT count, so an upload interrupted by minimizing the browser repeatedly never exhausts its budget. Retries also park on `_whenVisible()` while hidden. `MAX_TOTAL=60` is an absolute backstop. Server 408/429/5xx bounded to 4; everything else (401, etc.) terminal immediately. NOTE: a killed in-flight chunk re-sends fully (no server-side resume), so its progress-bar slice resets - completed chunks stay done. `pollForJSON` likewise treats pure network errors as non-fatal until the deadline. Every chunk reads `slice.arrayBuffer()` BEFORE sending: on Android a gallery-picked file can become unreadable (Google Photos cloud-sync / file changed = ERR_UPLOAD_FILE_CHANGED), which otherwise looks like "Failed to fetch" forever - the explicit read turns it into a terminal "select the file again" error. The error card shows a stage+raw-error detail line and an expandable console log (`consoleLog` ring buffer) for mobile bug reports.

**Metadata probe deadline (2026-08-13, iPhone field reports)** — `getVideoMeta`/`getAudioMeta` in `app.js` resolve `{duration:null,...}` after `META_PROBE_DEADLINE_MS` (7s). iOS Safari (notably Low Power Mode) can defer blob-video loading and fire NEITHER `loadedmetadata` NOR `error`; without the deadline `handleFile`'s await hung forever - attached card visible, Run never enabled, no error card, no telemetry. Null meta was already a handled path (size-only detail, checks skipped, Run enabled; the server re-probes duration at spawn). Known accepted edge: a >10-min video whose probe timed out under-declares duration and hits the server's `credit_mismatch` terminal (refunding) instead of a pre-upload warning. Test: "iOS silent-hang guard" in `tests/frontend/checklist.spec.js` (media `src` setter swallowed + `page.clock`).

**File byte snapshot at selection (design, 2026-07-09)** — the deeper fix for the Google-Photos-cloud-file problem above. `handleFile` calls `snapshotFile(file)` the moment a file is picked and slices the upload from that stable copy (`chunkedUpload(file, source, onProgress)` — `source` is the snapshot, `file` stays the metadata/resume-signature source). Rationale: a cloud-only file's reference goes stale *during* a long upload (background sync moves it), so lazy per-chunk reads fail partway; copying the bytes ONCE while the reference is still valid immunizes the upload. Two backends by size: `≤ SNAPSHOT_MEM_LIMIT` (150 MB) → in-memory `Blob` from `arrayBuffer()`; larger → IndexedDB (`hebpipe-uploads`/`blobs`, disk-backed/off-heap) put-then-read-back a stable copy. Either read throws on a truly unreadable (never-downloaded cloud) file, and `handleFile` **blocks at selection** with `file.cloud`/`file.cloudTitle` (a real warning telling the user to download to device first) — before any upload or credit spend. `_disposeSnapshot()` frees it on successful upload, on Clear-file, and at the start of the next snapshot; `_idbClearAll()` runs on load to wipe orphans from a prior "start over" reload (a reload can't resume an in-memory File anyway).

**Chunk upload protocol & CORS (2026-07-09)** - chunk POSTs go to a FIXED url `/upload_chunk/` with `key`/`index` in **headers** (`X-Upload-Key`/`X-Upload-Index`), not the query string. A chunk POST always triggers a CORS preflight (Authorization + `application/octet-stream` are non-safelisted); a constant url lets the browser reuse ONE cached preflight (`Access-Control-Max-Age=86400`, set on the OPTIONS response in `app()`) for the whole upload instead of re-flying before every chunk. The backend reads the headers and **falls back to the query string** (`?key=&index=`) so an old-frontend/new-backend deploy window still works, and so `test_api.py` (query-based) still exercises the endpoint. Deploy backend before frontend.

**Chunk upload tuning & resume (2026-07-09)** - `CHUNK_SIZE=1 MB`, `UPLOAD_CONCURRENCY=6`, `CHUNK_STALL_MS=35 s` (history: 5 MB/6 → 2 MB/4 → 1 MB/6). On congested café Wi-Fi (~5 Mbps up) 2 MB chunks each crawled ~20 s and a brief hiccup tripped the 20 s stall watchdog, aborting a live chunk and re-sending the full 2 MB → effective throughput fell to ~½ the link. Smaller 1 MB chunks finish ~2× faster (clearer liveness, less wasted on an abort); the 35 s watchdog only aborts a truly dead socket, never a slow-but-moving one; overhead stays low because all chunks share one cached preflight. **Telemetry**: `chunkedUpload` records `window.__lastUploadStats` (`mb`, `secs`, `mbps` effective, `stalls`, `netRetries`, `serverRetries`, `resentMB`), `console.info`s a summary (captured in the debug ring buffer), and surfaces a line in `#uploadStats` (visible on mobile, no devtools) so a slow upload is measurable (link-bound vs. our churn) instead of guessed. **Resume**: completed chunk indices are saved to `localStorage` keyed by a file signature (`name_size_lastModified`, `UPLOAD_RESUME_TTL=24h` < server's 48h scratch prune); `chunkedUpload` reuses the saved upload key and skips already-sent chunks, so a "try again" (same File) or reload+re-pick resumes instead of restarting. Cleared on full success. A `#uploadNote` ("keep the window open while uploading; you can switch away once processing starts") shows during the upload phase only - uploads run on the device via JS and CANNOT progress while the tab is backgrounded (the OS freezes it); processing/burn are server-side and survive backgrounding.

**Chunk streaming** — `upload_chunk` writes each chunk to a separate Volume file. `process_video` reassembles them with `shutil.copyfileobj` directly to the tempdir, one chunk at a time. This keeps RAM usage flat regardless of video size.

**R2 direct upload — the fast web path (2026-08-06)** — chunk POSTs to the Modal ingress are capped at ~3-4 Mbps regardless of client settings: the browser coalesces every concurrent request onto ONE HTTP/2 connection (per-origin), and the h2 upload flow-control window on the ~120 ms path to us-east-1 is the ceiling (measured; HTTP/1.1 single-conn 5.3 Mbps, 6 real TCP conns 10+ Mbps, same uplink to R2 21 Mbps = uplink-bound). The R2 S3 endpoint speaks HTTP/1.1 only, so parallel XHRs get REAL parallel connections. Flow: `POST /upload_r2/init/` (authed; body `{key,size}`) creates a multipart upload on the backup bucket (object `uploads/u{uid}__{key}.src` — uid-namespaced) and returns presigned part URLs (8 MB parts, 4 h TTL); the browser PUTs parts straight to R2 (no auth header — signature in URL; `r2Upload` in `app.js` reuses the chunked path's stall-watchdog/visibility/retry machinery and resumes via localStorage `<sig>_r2` with saved part ETags, TTL 3 h); `POST /upload_r2/complete/` assembles the object, streams it onto the volume as `chunk_0000` (staging + atomic replace — the exact `/upload_stream` shape, so processing/pending-spawn/retention/reload-resume are untouched), deletes the R2 object, and spawns a registered deferred job. `/complete` is IDEMPOTENT (existing `chunk_0000` short-circuits) so the client retries it safely. The deferred registration keeps the CHUNKED `total_chunks` count — one landed file never trips `_pending_complete` early; `/complete` is the only spawner on this path. **Fallback is load-bearing**: any R2-specific failure (init non-OK, part PUT dead while no part ever succeeded = bucket CORS unset, unreadable ETag = CORS missing `ExposeHeaders`) throws with `r2Fallback` and the caller runs the classic `chunkedUpload` with the SAME key — deploys are safe with zero R2 config. `_probeUplinkMbps` probes the R2 path first (`GET /upload_r2/probe/` → presigned PUT+DELETE pairs; plain fetch, never `apiFetch` — telemetry must not tear down a session) and falls back to the Modal probe. Start Over calls `_r2AbortActive()` (keepalive) before reloading. `api()` mounts the `hebpipe-backup` secret; missing creds → 503 `r2_unavailable` → fallback. **Native Android rides R2 too (2026-08-06, no APK change)**: `nativeUpload` first asks init for `single: true` — ONE presigned PUT for the whole file (the foreground service can't slice parts; the shipped plugin already does binary PUT, so only the target URL changes — and headers MUST be `{}` in R2 mode: the presigned URL is the auth). Single-conn HTTP/1.1 to R2 measured 15.4 Mbps vs ~3-4 through the Modal h2 ingress. An S3 PUT is atomic (object exists == whole file arrived); on the `completed` event the app POSTs `/upload_r2/complete/` `{key, single:true}` (head_object instead of multipart assemble). Close-and-forget is preserved by **`sweep_r2_uploads`** (scheduled every 5 min): for each pending registration ≥60s old with no `chunk_0000` on the volume, it heads `uploads/<full_key>.src` and if present lands it (`_r2_land_on_volume`, shared with the route) and spawns via **`_spawn_pending_job_impl`** — the old `_spawn_pending_job` closure body extracted to module level; the request-path delegate passes `expect_uid=uid` (registrant check), the sweep passes None (it acts on the registration record itself). Reconcile in R2 mode calls `/upload_r2/complete` instead of the `upload_check` byte probe (no chunk files ever land, the probe reads 0 forever); a complete that keeps failing falls into a ~7-min `process_pending` wait for the sweep (`r2NoFallback` — the bytes are in R2, re-uploading is wrong). Any pre-PUT R2 failure falls back to `/upload_stream` (same key; registration `total_chunks=1` fits both). `_cancelActiveNativeUpload` also fires `/upload_r2/abort` (keepalive). **Parallel native uploads (2026-08-06, needs the NEXT Android binary)**: the custom `ParallelUploader` Capacitor plugin (`ParallelUploaderPlugin.java` + `ParallelUploadService.java`) runs N=5 concurrent byte-range PUTs to presigned part URLs inside its own foreground service (single connection ≈ 9 Mbps in the field vs ~20 web) and then completes the multipart DIRECTLY against R2 via a presigned `complete_multipart_upload` URL (init `parallel: true` returns `urls` + `complete_url` + `abort_url`; the XML body is unsigned so any HTTP client can POST it) — the assembled object exists even if the app dies, so the sweep recovers it; the JS `completed` handler still calls `/upload_r2/complete` `{single:true}` as the fast path (works because the object exists). The plugin mirrors the stock uploader's event contract (`{name,id,eventId,payload}`, persisted terminal events + `acknowledgeEvent`) so `_nativeUploadRun` drives both via a `mode` param; preference order: ParallelUploader → single-PUT stock → `/upload_stream`. `_rememberActiveNativeUpload` stores WHICH plugin so Start Over cancels the right one. `MainActivity.onDestroy`'s `stopAllUploads` deliberately does NOT stop this service (sweep makes finish-after-swipe-away correct). S3 quirk handled: CompleteMultipartUpload can answer 200 with an `<Error>` body — the service verifies the body. Tests: parallel cases in `native_upload.spec.js`, `test_parallel_mode_presigns_complete_and_abort` in `test_asgi.py`. **Bucket prerequisites (one-time, needs an Admin R&W R2 token — the object-level backup token gets AccessDenied): run `modal run scripts/r2_bucket_setup.py`** to set CORS (allow PUT+DELETE from the app origin, EXPOSE `ETag` — without it every part "succeeds" but the multipart can never complete) and a 2-day lifecycle expiry on `uploads/` (orphan sweep; the happy path deletes eagerly). In `mockAllApis`, `/upload_r2/*` answers 503 by default so every existing spec exercises the chunked path; `r2_upload.spec.js` re-registers the routes (last wins) and mocks the cross-origin part PUTs incl. preflight + ETag expose. Tests: `TestR2Upload` in `tests/backend/test_asgi.py`, `tests/frontend/r2_upload.spec.js`.

**Assembler page rides R2 too (2026-08-16)** — `site/assembler.html` (`uploadFile`) uses the same init → part PUTs → complete flow with its own compact client; `/complete` only spawns when a `pending_store` registration exists, so for assembler keys it just lands `chunk_0000` (see `docs/assembler.md`). Keep `/complete` spawn-gated on the registration - an unconditional spawn there would start a paid /process job for every assembler upload.

**Native upload reconcile — /process_pending is the source of truth (2026-07-16)** — while backgrounded the WebView is frozen, so the `Uploader` plugin's `completed` event can be LOST; `nativeUpload`'s `reconcile()` (on `visibilitychange`→visible) must confirm with the server. It checks `/process_pending/?key=` FIRST — a `call_id` means the upload landed and spawned; the `done:<key>` Dict marker lives 48h. The `upload_check` byte probe is only the in-flight fallback (also refreshes the progress bar): `process_video` **deletes chunk files at reassembly** (`p.unlink()`), so once processing starts the byte check reads 0 forever — relying on it alone caused the stuck-at-"5% uploading" bug (reopen after the ready push → frozen upload UI, never settles). Also never gate the pending check on `desc.size` (`expected`) — a picker that reports no size would disable reconciliation entirely. Regression test: `tests/frontend/native_upload.spec.js` ("a lost 'completed' event recovers…").

**Native uploads always use the Android foreground service (2026-07-29)** — every file selected in the Capacitor app, including videos ≥150 MB, goes through `nativeUpload` / `@capgo/capacitor-uploader` and `/upload_stream`. This is what keeps the transfer alive when the app is minimized or the phone locks, and it owns the visible Android upload notification. Do NOT route large native files through the WebView `chunkedUpload`: that path has per-chunk resume, but Android freezes its JavaScript in the background and no status-bar notification exists (the shipped ≥150 MB split caused this field report). Web uploads remain chunked/resumable. The native stream uploader retries the whole request from byte zero after a network failure; that tradeoff is deliberate in favor of reliable background behavior. `/upload_stream` must receive into a unique staging file, treat `http.disconnect` as failure (never EOF), verify `X-Upload-Size`, then atomically publish chunk 0000 before spawning. Otherwise a weak connection can start ffprobe on a partial MP4 while Android is still retrying. The uploader plugin persists terminal events: `nativeUpload` must filter every event by the `id` returned from `startUpload` and acknowledge terminal `eventId`s, or a stale completion from an older upload can release a new upload early. Persist the active upload id/key while it runs; Start Over must call `Uploader.removeUpload({ id })` before reloading, then POST `/cancel_upload/` to discard the deferred registration and partial server file. Android may surface that deliberate stop as a generic `failed: Cancelled by user` event rather than `cancelled`; while Start Over is active, suppress both forms and reload immediately instead of flashing an error card. Regression tests: `tests/frontend/native_upload.spec.js` and `tests/backend/test_asgi.py::{TestReceiveStreamUpload,TestCancelStreamUpload}`.

**Upload progress notification needs POST_NOTIFICATIONS (2026-08-22, field report "the notification with the progress bar stopped")** - on Android 13+ the OS hides EVERY notification, including the foreground upload service's progress bar (ParallelUploadService / gotev), unless the runtime permission is granted; the app used to ask exactly once, via the push prompt in `_initPush` at login, so one "Don't allow" (or a reinstall) silently removed the upload notification for good with no signal in the app. `_ensureNotifPermission()` now runs at the start of every `nativeUpload`: re-raises the OS prompt while the state is still `prompt`, and when it is denied shows the `upload.notifOff` toast once per session telling the user to enable notifications in the phone settings (no in-app settings deep link - the `NativeSettings` plugin is not shipped). The upload itself is never gated on the permission. Tests: the three "notifications ..." cases in `tests/frontend/native_upload.spec.js`.

**Deferred-spawn done-marker must die at re-registration (2026-07-16)** — the chunked upload key is derived from the FILE SIGNATURE (`_resumeUploadKey`), so re-processing the same file reuses the key, and `/process_pending` checks `done:<key>` FIRST (before the pending registration). A stale marker from a previous run (lives 48h) therefore short-circuited every resume/reconnect poll to the OLD call_id — the user got the old result rendered with the OLD toggles ("silences cut although the toggle is off") while the new job spawned and consumed a credit unseen. Fix: the `defer=true` registration pops `done:<full_key>` BEFORE writing the new registration (order matters — once the registration exists no poll may see the old marker), and the direct `/process` spawn pops it too. NOT a frontend bug: the toggles were verified to reach `process_video` correctly on all three spawn paths. Tripwire test: `tests/backend/test_asgi.py::TestDoneMarkerInvalidation` (route bodies are closures — the test guards the source).
