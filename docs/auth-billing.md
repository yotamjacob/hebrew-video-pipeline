# Auth, quota, credits & billing

Deep contracts moved out of CLAUDE.md (2026-08-09) to keep the always-loaded core lean.
**Read this file fully before changing** auth/sessions, tokens, signup, quota/credits, Play billing, throttles, or admin surfaces. Everything here is load-bearing;
update it in place when behavior changes.

**Rate limiting scope** — `_check_rate_limit` uses an in-memory dict per Modal container instance (10 req/60 s per IP). Multiple concurrent container instances each have their own limit — effective limit is `10 × N_instances` per minute. Sufficient for abuse prevention; not a per-user quota.

**Signup source attribution (2026-07-16, campaign links)** — a shared link like `https://hebrew-pipeline.app/?src=linkedin` (`utm_source` also accepted) is captured at load in `app.js` (sanitized `[a-z0-9_-]{1,32}`, lowercased) and persisted to `localStorage.hebpipe_src` — the visitor often signs up on a LATER visit, so the query string alone wouldn't survive. Sent as `src` with `/auth/verify-code` and `/auth/google`; the backend `_signup_src()` (nested in `api()`, `app_modal.py`) re-sanitizes and records `signup_src` on NEW user records only (sign-in never overwrites). `/admin/users` returns it as `src`; the Admin tab shows it as an `.admin-src` badge next to the email. Tests: `tests/frontend/auth.spec.js` ("?src= campaign link…"), `quota.spec.js` (admin badge).

**Quota-exhausted purchase CTA** — in a current native Android shell, both quota surfaces (the pre-spawn `#noticeBlock` and the server-402 error card) open the Google Play credit-pack modal via `#noticeBuyCta`/`#errorBuyCta`. On the web, `#noticePlayCta`/`#errorPlayCta` link only to the Pipeline Play Store listing (`com.heb.pipeline`) so payment remains Play-only; older native shells without `NativeBilling` use the same link with “update app” copy. There is deliberately no WhatsApp/payment fallback on quota surfaces (WhatsApp is gone from the app entirely as of 2026-08-08; support goes through the footer contact email). `showBlockNotice` and `showError` must hide both purchase variants before revealing the platform-appropriate one. **Admins keep the pill too (2026-07-31)** — they bypass the quota, so `updateQuotaUI` renders it as a plain `billing.buyCredits` action with no count instead of hiding it, and `openQuotaPurchase` lets `_isAdminUser()` reach the Play listing on web (an admin has no exhausted state, so the `_quotaExhausted()` gate alone made their pill dead). Billing init/restore were never role-gated, so the purchase path itself already worked. Tests: `tests/frontend/quota.spec.js`, `tests/frontend/play_billing.spec.js`.

**Auth & per-user data isolation** — email+password accounts (`hebpipe-users` Dict, PBKDF2-600k hashes; the account key is the lowercased email — legacy pre-2026-07 accounts remain keyed by username and can still log in with it, or with their attached email via the `email:{addr}` reverse index; identifiers containing `:` are rejected so they can never collide with the `uid:`/`email:` index namespaces), stateless HMAC session tokens signed with `AUTH_SECRET` from the `hebpipe-auth` Modal Secret (30-day expiry). **Signup is OPEN as of 2026-08-01** - the `INVITE_CODE` gate is GONE from every path (email-code, Google, and the dead password-register branch, which was deleted with it); `INVITE_CODE` may stay in the secret but nothing reads it. Rationale: Google rejected production access partly on "the app was not ready", and a reviewer with no invite code cannot get past the login wall. The remaining new-account gate is Terms acceptance (a legal requirement, kept). With the invite gone, the abuse ceiling is the verified email itself plus the per-email/per-IP code-send throttles, and the free-tier grant - so `DEFAULT_VIDEO_LIMIT` is pinned at 3 by `TestOpenSignup` in `tests/backend/test_asgi.py`, which also fails if any invite comparison returns. The Google flow answers a missing Terms box with BOTH `need_terms` (current clients) and `need_invite` (installed shells that only know that flag) so either build reveals the checkbox and retries with the ID token it already holds. The uid comes ONLY from the verified token. Every volume key is namespaced `u{uid}__` by the router; workers derive output-key prefixes from their input keys (`_UID_PREFIX_RE`); `/download`, `/thumbnail`, `/jobs`, `/burn` etc. enforce `_owned_key`; every spawn records `call_id → uid` in `hebpipe-calls` and all `*_poll`/`/cancel` routes verify it. Public (tokenless) routes: `/`, `/auth/register`, `/auth/login`, `/oauth/callback`, `/media/*` (Metricool's ingester fetches it; keys are unguessable). GET requests may pass the token as `?token=` — but NOT the session token: they pass a short-lived **media token** (see below). Frontend: `apiFetch()` adds the Bearer header and drops to the login view on 401; token in localStorage. Metricool OAuth connection remains global (single brand account), not per-user. Supabase migration path: swap `_verify_token` for provider-JWT verification mapping to the same uid.

**Play-review demo login (2026-08-01)** — sign-in is passwordless (Google or a 6-digit code we email) and a Google Play reviewer can use NEITHER, which is the most likely reading of the "app was not ready" production-access rejection. So ONE address signs in with a FIXED code: `REVIEW_EMAIL` + `REVIEW_CODE` in the **`hebpipe-review`** Modal secret (its OWN secret — adding a key to `hebpipe-auth` needs a `--force` rewrite that replaces every key, and the existing values can't be read back; to disable, BLANK `REVIEW_CODE` rather than deleting the secret, which the deploy still references). `_is_review_email` / `_review_login_ok` (`pipeline_core.py`, both no-ops when the secret is unset) are pure and unit-tested. Wiring: `/auth/request-code` short-circuits the address BEFORE the lane-mismatch and Terms checks (returns `{ok, is_new:false}`, sends no mail) so EITHER lane reaches the code screen and the account need not exist yet; `/auth/verify-code` checks the fixed pair AFTER the per-email/per-IP verify throttles (so the fixed code is not freely brute-forceable) and synthesizes a `crec` so the normal find-or-create runs unchanged. A wrong guess falls through to the ordinary path and answers `code_expired`, revealing nothing. The record is a NORMAL user — deliberately never `role="admin"`, since the Admin tab lists every user's email — flagged `review_account: True`, and its `video_limit` is set to `_count_quota_used(...) + REVIEW_VIDEO_LIMIT` (25) on EVERY login: topping up past the authoritative consumed count is what actually restores credits, because the gate takes `max(record_used, quota-key scan)` and resetting `videos_used` alone would do nothing. Rotate or blank the code once Play grants production access. Tests: `tests/backend/test_review_login.py`.

**Media token (GET-media-scoped)** — the 30-day session token must never ride in a query string (logs/history leak). `_sign_media_token`/`_verify_media_token` in `pipeline_core.py` mint a 1h token (format `m.<uid>.<exp>.<sig>` — 4 parts, disjoint from the 3-part session token so the verifiers can't be confused). `GET /auth/media-token` (session-authed) returns one; the site caches it (`mediaToken` in `app.js`, refreshed every 45 min via `refreshMediaToken()` called from `showApp()`), and `_withToken()` uses it, falling back to the session token only until the first one arrives. The session guard accepts a media token via `?token=` ONLY on GET requests — never for mutations.

**Email layer (Resend)** — ⚠️ PARTIALLY DEFERRED: `EMAIL_UI_ENABLED = false` in `site/app.js` hides the verify banner, forgot-password link and the update/promo consent checkbox — but since 2026-07-07 the account identifier IS an email, and since 2026-07-13 signup is passwordless (Google or a 6-digit email code + a mandatory Terms checkbox). `/auth/register` is a bare 410 and its handler body was DELETED on 2026-08-01 along with the invite gate — re-enabling password registration means writing it again, not un-commenting it. The login code is itself proof of the address, so no separate verification mail is sent on signup. To re-enable the rest of the email UX, flip `EMAIL_UI_ENABLED` to true (the backend routes below still exist and work). The rest of this note describes the flow WHEN enabled: accounts collect an email at registration and get a verification email; verification is a **nudge, not a gate** (`email_verified` on the record; `/auth/me` returns `email` + `email_verified`; the site shows a dismissible banner). Routes: `/auth/verify` (public GET, HTML page), `/auth/request-verification` (authed POST, also sets/updates the address), `/auth/forgot` (public POST, always 200 — never reveals account existence), `/auth/reset` (public POST). Reset/verify links carry a scoped one-time token (`_sign_scoped_token`/`_verify_scoped_token`, scope `verify`|`reset` baked into the HMAC message so they're not interchangeable; verify TTL 7d, reset TTL 1h). `_send_email` posts to Resend and is **best-effort** — no `RESEND_API_KEY` just logs and skips, so sign-up never fails on mail. Secret keys needed in `hebpipe-auth`: `RESEND_API_KEY`, `EMAIL_FROM` (verified-domain sender), optional `SITE_URL` (reset links; defaults to the Vercel alias). `email:{addr}` reverse index in `hebpipe-users` powers forgot-by-email. Signup gate: **Terms/Privacy acceptance is mandatory** (`authTermsCheck` → `terms_accepted`, enforced client-side via `authSubmit`→`auth.termsError` AND server-side `/auth/register` 400s without it; `terms_accepted_ts` recorded). The update/promo consent checkbox (`auth.marketing` → `marketing_consent`) still exists in the markup but is **hidden while `EMAIL_UI_ENABLED=false`** and not sent; if re-enabled, see git history for the prior ⚠️ compliance note (mandatory consent to *promotions* violates Israeli Comms Law Amdt. 40 / GDPR — make that box optional or split promotions into a separate opt-in).

**Credit pricing (2026-07-31)** — a credit is no longer a flat "one video". `_credit_cost(duration, enhance_video)` in `pipeline_core.py`: one credit covers `CREDIT_SECONDS` (600) of source, a longer video adds one, and `esrgan` adds `UPSCALE_CREDIT_COST` (1). `CREDIT_DURATION_TOLERANCE` (5s) keeps a float 600.4 from doubling the price of a video the user thinks is exactly 10 minutes. The 4K upscale is REFUSED above `UPSCALE_MAX_SECONDS` (180) by `_upscale_allowed` — at 15-30x realtime it would exceed `process_video`'s 1800s timeout, and a timeout refunds the credit AFTER the GPU time was spent. The client sends its measured `duration` on `/process` and mirrors the rule (confirm-modal copy + a disabled `#ev_esrgan` with `#upscaleLimitNote`), but the price is authoritative on the server: `process_video` takes `credits_charged` and re-prices from its OWN probe right after it, raising terminal `credit_mismatch` / `upscale_too_long` if the client understated things — so lying buys nothing (and a terminal raise refunds). Multi-credit runs write one unique quota key each via `_charge_credits` (first key keeps the historical `{uid}:{call_id}` shape, extras are `#2`, `#3`) and `_refund_credits` returns ALL of them, idempotently. The deferred registration carries `credit_cost` because the upload endpoint has no query string to re-read. Free tier is `DEFAULT_VIDEO_LIMIT = 3` for NEW records; `LEGACY_VIDEO_LIMIT = 5` is the fallback wherever an existing record is READ (`_quota_state` + the two `base_video_limit` sites), which grandfathers pre-2026-07-31 users with no explicit `video_limit` and is why no data migration was needed — never lower that fallback. Play packs are now 10/30/100 (₪59/₪149/₪399); the retired 5/20/50 IDs stay in `PLAY_CREDIT_PRODUCTS` + `BILLING_CREDITS` while they are live in Play. The map is forward-only (grants store their credit count at purchase time), so editing it never revalues a past purchase. Tests: `tests/backend/test_credit_cost.py`, `TestCreditCharging` in `test_asgi.py`, `tests/frontend/credit_cost.spec.js`.

**Video quota (free tier)** — every `/process` spawn consumes one credit. `_quota_state`/`_quota_allows` in `pipeline_core.py` (`DEFAULT_VIDEO_LIMIT = 3` for new records, `LEGACY_VIDEO_LIMIT = 5` when reading an existing one — see the credit-pricing note above; `videos_used`/`video_limit` live on the `hebpipe-users` record; `video_limit = -1` = unlimited). Admins bypass: `role: "admin"` on the record OR username in the optional `ADMIN_USERS` env var (hebpipe-auth secret). `/auth/me` returns role + usage (drives the site's quota pill + Admin tab visibility); `/admin/users` + `/admin/limit` (admin-only) power the Admin tab. A 402 `limit_reached` is mapped client-side to a friendly i18n message that never names a person. Increment happens at spawn; **a terminally-failed job is refunded** — the `/process_poll` error handler (only reached on a real job failure, not "still running") deletes the unique `{uid}:{call_id}` quota key (authoritative refund) and decrements `videos_used` (display floor), idempotently so concurrent polls can't double-refund. Frontend `showError` calls `refreshQuota()` so the pill reflects the refund. Best-effort; a network-only poll failure that didn't actually fail the job would over-refund (errs in the user's favor).

**Key validation pattern** — `_SAFE_KEY_RE` and `_SAFE_DOWNLOAD_KEY_RE` at module level validate upload keys and download keys before any filesystem access. Keys must be `[a-zA-Z0-9_\-]` (plus `.` for downloads), max 128 chars.

**Quota is race-proof via unique keys** — the `videos_used` counter on the user record is display-only; the authoritative consumed-credit count is `_count_quota_used(quota_store, uid)`, a scan of unique `{uid}:{call_id}` keys in the `hebpipe-quota` Dict written one-per-spawn. This avoids the lost-update race a mutable counter has under concurrent `/process` calls (modal.Dict has no atomic incr/CAS). The gate uses `max(record_used, scan_count)` so the record is a floor (existing usage survives migration). Overshoot is bounded to genuine concurrency, never unlimited.

**Google Play Billing (2026-07-30)** — Android binary 1.3.0 registers the custom `NativeBilling` Capacitor bridge (`NativeBillingPlugin.java`) on Play Billing Library 9.1.0. It exposes `getProducts`, `purchase`, and `restorePurchases` for the consumable IDs `pipeline_credits_5`/`20`/`50`; localized prices always come from `ProductDetails`. In a current native shell the quota pill is always actionable, even with credits remaining, and carries a compact `+` affordance; web/old-native Play routing remains exhaustion-only. Billing flow binds `setObfuscatedAccountId(sha256("hebpipe-play:"+uid))`. The client sends the purchase token to authenticated `POST /billing/play/verify`; the backend calls ProductPurchaseV2, requires `PURCHASED`, matching product + account hash, stores a durable grant under `play:<sha256(token)>` in `hebpipe-purchases`, then consumes the token. Credits are derived by summing unique active grants, never by incrementing a mutable balance, so callbacks/restores are idempotent. Grant-before-consume is deliberate: a consume outage sets `consume_pending` and app restoration retries without double credit. `reconcile_voided_play_purchases` runs every six hours against Play's Voided Purchases API and marks refunded/charged-back grants `revoked`, which removes them from effective quota without storing raw tokens. `PLAY_SERVICE_ACCOUNT_JSON` is preferred, with the mounted `FCM_SERVICE_ACCOUNT` as fallback; its email must have Play Console purchase/order permission. `PLAY_RELEASE.md` is the product/credential/test checklist. Tests: `tests/backend/test_play_billing.py`, `tests/frontend/play_billing.spec.js`.

**Apple in-app purchase (2026-08-11)** — the iOS binary registers a StoreKit 2 `NativeBillingPlugin.swift` under the SAME bridge name (`NativeBilling`) and the same JS surface as the Android plugin, so `site/app.js` runs ONE billing flow and only branches on the verify endpoint. Products `pipeline_credits_10/30/100` (`APPLE_CREDIT_PRODUCTS` in `pipeline_core.py`; no retired Apple ids yet). Binding is `appAccountToken` = `_apple_account_token(uid)`, a deterministic UUID folded from `sha256("hebpipe-apple:"+uid)` — a DIFFERENT namespace from the Play hash so neither can be replayed as the other, and UUID-shaped because StoreKit rejects anything else. The client sends ONLY `transaction_id` to authed `POST /billing/apple/verify`; the server calls the App Store Server API (`_fetch_apple_transaction`, production host first then `api.storekit-sandbox…` on 404 — App Review and TestFlight are always Sandbox), and `_parse_apple_transaction` requires the right bundle, a known consumable product, no `revocationDate`, and a matching account token. Grants land in the SAME `hebpipe-purchases` ledger under `apple:<transactionId>` (the raw id, unlike Play's hashed token — a StoreKit id is not a bearer credential; `_APPLE_TXN_RE` keeps it inside the namespace), and `_count_purchased_credits` sums `PURCHASE_KEY_PREFIXES` = `("play:", "apple:")` so a user who bought on Android keeps those credits inside the iOS app. **There is no consume step**: a StoreKit consumable is finished ON THE DEVICE, and the JS finishes it only AFTER the grant returns (`purchase → /billing/apple/verify → finishTransaction`), because before the grant an unfinished transaction is the user's only proof of purchase — an interrupted run is re-offered via `Transaction.unfinished`/`Transaction.updates` and the idempotent route grants it exactly once. Refunds arrive at PUBLIC `POST /billing/apple/notify` (App Store Server Notifications V2, wired ABOVE the session guard); the body is untrusted and used only to learn which transaction to re-fetch from Apple, so a forged notification achieves nothing — unparseable bodies answer 200 (never retriable), an Apple/API failure answers 500 so Apple resends. Credentials live in their OWN `hebpipe-apple` secret (`APPLE_KEY_ID`, `APPLE_ISSUER_ID`, `APPLE_PRIVATE_KEY`; absent → 503, so a deploy before the key exists stays healthy) and `_appstore_jwt` signs ES256 with `bid` scoped to the bundle. `APPLE_RELEASE.md` is the product/credential/submission checklist. Tests: `tests/backend/test_apple_billing.py`, `TestAppleBillingRoute` in `test_asgi.py`, `tests/frontend/ios_store.spec.js`.

**iOS store-compliance gating (2026-08-11)** — `_isIOS()` (native AND `Capacitor.getPlatform() === 'ios'`; Safari on an iPhone is still `web`, and the WEBSITE is deliberately unaffected) drives three App Store rules in `site/app.js`. **3.1.1**: `_playStoreCtaAllowed()` is false on iOS, so `#noticePlayCta`/`#errorPlayCta`/`openQuotaPurchase()` can never surface a Google Play link even if the StoreKit bridge fails to register, and `_tStore(key)` prefers a `<key>.ios` i18n entry so no billing copy names another store (`_syncStoreCopy()` re-points the static `billing.secure` footnote after every `applyI18n`, i.e. on boot and on every language switch). **4.8**: `_setupGoogleAuth()` hides the Google button, `#gsiButton` and `.auth-or` on iOS and swaps the hint to `auth.newHereEmail` — offering only the email-code lane puts 4.8 out of scope entirely, which is why Sign in with Apple was NOT built. **5.1.1(v)**: `deleteAccountFlow()` (footer `footer.deleteData` on every view) runs a two-step confirm then `POST /account/delete`; signed OUT it still opens the `delete-account.html` explainer. The route purges the volume prefix, jobs/costs/progress/pending/quota/errors/calls/fcm and the account record plus both index entries, and ANONYMIZES purchase grants (uid dropped, state revoked) rather than deleting them, since they are financial records. Because the session token is a stateless 30-day HMAC that outlives the record, `/process` now 401s `account_deleted` when `_user_by_uid()` finds nothing — otherwise a kept token would still spawn jobs on the free-tier fallback limit.

**Brute-force throttle** — `_check_rate_limit` is only a per-container burst cap. Real password/login-code protection is `_throttle_allowed`/`_throttle_record_fail`/`_throttle_clear` over the persistent `hebpipe-throttle` Dict (8 fails / 15 min rolling window, cross-container). Login throttles on `login:{username}` AND `loginip:{ip}`; code sends on `code:{email}` AND `codeip:{ip}` (the old `invite:{ip}` key went away with the invite gate). Fails **open** if the store is unavailable. Cleared on success.
