## Pipeline Steps

1. `extract_audio()` — ffmpeg extracts 48 kHz mono WAV
2. `enhance_*()` — ElevenLabs API / Adobe Podcast manual / skip
3. `transcribe()` — faster-whisper (`ivrit-ai/whisper-large-v3-ct2`, the full non-turbo model — more accurate than turbo on clean audio), word-level timestamps, biased by `WHISPER_INITIAL_PROMPT` (well-formed Hebrew). On Modal, `process_video` then runs `proofread_words` (Sonnet 5) over the word list to fix Hebrew ASR mishearings using full-sentence context (homophone swaps, wrong conjugations, same-sounding non-words like `קולטה`→`כל תא`) — array length/order preserved so each element still maps 1:1 to its audio span and timestamps stay valid (a merged-word element may hold a multi-word phrase sharing that token's timestamp); best-effort (any failure keeps the raw transcript)
4. `compute_keep_segments()` — **word-level** speech-keep detection: cuts on word gaps ≥ `min_silence` (now also WITHIN a Whisper segment, not just between them) and tightly excises `filler`-flagged words; adds padding around kept speech. See "Silence cutter: noise + filler rejection" below.
5. `generate_ass()` — builds ASS subtitle file; remaps timestamps to post-cut video
6. `final_render()` — single ffmpeg pass: trim → concat → burn captions → H.264 CRF 18

## Key Defaults

DEFAULT_MIN_SILENCE = 0.3      # gap (s) to treat as silence

## Non-Obvious Details

**ffmpeg binary selection** — prefers Homebrew `ffmpeg-full` (`/opt/homebrew/opt/ffmpeg-full/bin/ffmpeg`) over generic `ffmpeg` because `ffmpeg-full` includes libass (needed for burning subtitles).

**CUDA fallback** — `transcribe()` tries float16 on CUDA first; auto-downgrades to int8 on CPU. No manual config needed.

**ASS color format** — `&HAABBGGRR&` (reversed RGB, alpha first). Alpha `00` = opaque, `FF` = transparent.

**Burned caption ASS style (in `burn_captions_fn`)** — current values as of 2026-05-09:
- `BorderStyle=1, Outline=2, Shadow=0, Alignment=2` (bottom-center)
- `char_w = font_size * 0.50` for Python re-wrap (2026-07-12, was 0.60) — MEASURED Heebo advance is ~0.46/char (400 weight); 0.50 packs lines close to full while staying just above the real width so libass (same margins) never re-wraps. 0.60 wrapped ~25% early, leaving the allowed width underfilled. Do NOT drop below ~0.48 or libass may add extra breaks. Kept in sync in `build_caption_ass` + frontend `rewrapCaption` + `tests/backend/test_ass_generation.py`.
- Caption shadow is disabled (`Shadow=0`) — the user prefers no shadow on caption text.
- **libass font-size compensation (2026-07-16)** — libass sizes glyphs by the font's LINE metrics (hhea asc−desc) while CSS uses the em square, so at the same nominal size libass renders (asc−desc)/upem SMALLER — **Heebo: /1.469 ≈ 32% smaller** (measured pixel-wise vs Chrome; this was the "font changes when the preview pauses" report — the exact frame was truthfully showing a much smaller burn). `build_caption_ass` scales the Style Fontsize by `_LIBASS_FONT_SCALE[font]` (in-function so AST tests extract it; per-family factor = (hhea.ascent−hhea.descent)/unitsPerEm of the Google-Fonts TTF — Heebo 1.469 … Karantina 1.012 … Playpen 1.530) → burned size now equals the preview size. The wrap estimate (`char_w`) stays on the NOMINAL size (compensated libass advances == CSS advances of the nominal size), and every caption event carries `{\q2}` so libass can never re-wrap the pre-wrapped lines. Multi-line advance in libass = render_fs = nominal×factor, so the DOM overlay sets `line-height: <factor>` from the mirrored `LIBASS_FONT_SCALE` map in `app.js` (keep the two tables in sync; recompute when adding a font). NOTE: the old "export font size ×1.10" compensation is GONE (burnUrl sends the raw slider size). The HOOK is not yet compensated — its canvas-parity story needs its own verification before touching.
- **Captions are REAL bold (2026-07-17, replaced the faux-bold experiment)** — the images install STATIC Regular+Bold fonts.gstatic instances (`_FONT_CMDS` in `pipeline_core.py`, shared by all three images — the SAME files the css2 `<link>` serves the browser), and the caption Style sets `Bold=-1` so fontconfig resolves the true 700. One Dialogue event per caption with `{\q2}` (never re-wrap pre-wrapped lines). libass does NOT synthesize bold from a lone Regular (verified), so single-weight fonts (Secular One, Suez One) render 400 on BOTH sides — `#playerCap` has `font-synthesis: none` to match. The 2026-07-16 faux-bold (fill-colored outline layers) is GONE — it overshot true 700 and read as "bulky/thick border" on pause. NOTE: the hook still uses its own faux-bold (canvas-parity contract) — untouched. Pixel parity: Chrome real-bold ink 435px vs burn 438px (outline included) at nominal 48. Tests: `TestCaptionRealBold` in `test_ass_generation.py`.
- Export font size = the RAW slider size (`site/app.js` burnUrl) — the old ×1.10 is gone; size parity with the preview comes from the libass compensation below.

**Exact WYSIWYG preview — libass-rendered frame (2026-07-11)** — a browser Canvas/CSS preview can NEVER be pixel-identical to the burned video: the two use different text engines (browser vs libass/FreeType) with different glyph metrics, outline models, and variable-font bold handling (libass renders these Google fonts at ~400 and can't `\b` them; at the same nominal size libass also renders visibly SMALLER than CSS). So the caption/hook editor now shows the REAL thing: `POST /preview_frame` (router, `light_image` — now carries the Hebrew fonts + fontconfig) extracts the current frame, builds the ASS via the SHARED `build_caption_ass` (the SAME function `burn_captions_fn` uses — verified pixel-identical), burns it with ffmpeg/libass, and returns a PNG. The frontend overlays that still (`#exactCap` over the paused player, `#exactHook` over the hook canvas) — the fast Canvas/CSS preview stays as the INSTANT fallback during motion/dragging, and the exact frame swaps in on settle (400 ms debounce; `scheduleExactCap`/`scheduleExactHook`, hidden via `_hideExactCap`/`_hideExactHook` on play/seek/edit, cleared by `_resetExactPreview`). `build_caption_ass(width,height,font,font_size,margin_h,margin_v,captions,hook)` is module-level in `pipeline_fns.py` and is the SINGLE source of truth for caption+hook ASS — do NOT re-inline it. The endpoint retimes the active caption + hook to the extracted still (t=0) and sizes the ASS to the extracted PNG's real dims (sidesteps rotation). Tests: `tests/frontend/exact_preview.spec.js`; backend ASS-invariant tests now extract from `build_caption_ass`.

**Hook ASS rendering — vector box + preview-driven lines (rewritten 2026-07-11, WYSIWYG)** — the hook is NO LONGER auto-wrapped by libass. The old `{\q1}` soft-wrap + `BorderStyle=3/4` opaque box diverged from the canvas preview: libass fits MORE Hebrew per line than the browser's `measureText`, so the burned wrap (long line 1, short remainder) didn't match the balanced preview the user saw. Now:
- **Lines**: the frontend `drawHookPreview` wraps with `ctx.measureText` (what the user sees) and stores the result in `_hookLines`; `doBurn` calls `drawHookPreview()` then sends `hook.lines` in the `/burn` body. `burn_captions_fn` renders those EXACT lines (`\N`-joined, `{\q2}` = no auto-wrap). Fallback greedy wrap only if `lines` is absent (old client).
- **Box**: drawn as an explicit **vector rectangle** (`{\p1}` `m 0 0 l w 0 l w h l 0 h`) on layer 0, geometry copied from the preview's box math (`fs=min(w,h)·0.075·pct`, `edge=0.7·fs` [was 1.0·fs — reduced 2026-07-12 so the hook fills more width; MUST match frontend `drawHookPreview` edgePad], `maxW=w-2·edge`, `padH=0.55·fs`, `padV=0.35·fs`, `lineH=1.10·fs`, `boxW=maxW+2·padH` [≤ w since padH<edge], `boxH=n·lineH+2·padV`, vertically centered at the preview's clamped `cy`). Colour via `\c&HBBGGRR&` + `\1a` alpha. This gives pixel-parity with the preview box regardless of text width — no more per-line opaque boxes, no BorderStyle box at all.
- **Text**: layer 1, `{\an5\q2\pos(w/2, cy)}` centered block, white fill.
- **Weight (faux-bold)**: libass does NOT embolden the variable Google fonts (`\b`/`Bold=-1` is a no-op — verified: renders ~400), while the canvas preview uses true `bold`. So the burn thickens strokes itself with a **fill-colored outline** `\bord(fs·0.035)\3c<fillcolor>` (border_size=0 case), matching the preview weight deterministically on any libass build. Hook Style uses `Bold=0` so the outline alone sets weight. When `border_size>0`, the outline is the user's border colour, width `fs·border·0.10` (matches the preview's `lineWidth=border·2` canvas-px scaled to burn res).
- Hooks burn only via `burn_captions_fn` (the `hook_json` arg → the hook block in `build_caption_ass`). Verified by burning the real "pipeline-before" clip and diffing against the canvas preview (scratchpad harness). Tests: `tests/frontend/hook.spec.js` ("burn sends the exact hook lines").

**Caption timestamp remapping** — ASS cues are generated assuming the full uncut timeline, then shifted by the accumulated duration of preceding cut-out segments. This must stay in sync with the ffmpeg trim list.

**Modal warmup pattern** — `GET /warmup` fires `process_video` with `filename="__warmup__"` asynchronously to pre-warm the L4 GPU container. The real `/process` endpoint benefits on the next call.

**Whisper model cache** — first run downloads ~1.5 GB to the local faster-whisper cache; Modal uses a persistent volume so it survives redeployments.

**Web API base** — `https://yotamjacob--hebrew-video-pipeline-api.modal.run` (hardcoded in `site/app.js`).

**Font size auto-scaling** — the pipeline reads video resolution and adjusts `--font-size` and `--margin-v` proportionally so captions look consistent across 1080p and 4K.

**Prompt caching** — the Sonnet moment-selection system prompt is marked `cache_control: ephemeral`. The ~5-6k-token stable prefix is cached (comfortably above the model's minimum cacheable size); only the transcript (user message) changes per call.

**Sonnet 5 API constraints** — `temperature`/`top_p`/`top_k` are REJECTED (400) on `claude-sonnet-5`; all Sonnet call sites pass `thinking={"type": "disabled"}` instead (omitting `thinking` would run adaptive thinking, eating into `max_tokens`). Variety in hooks/captions comes from prompting, not temperature.

**`_process_moment` is a plain function by design** — it runs in a ThreadPoolExecutor inside `analyze_stock_broll`'s container. Do NOT add `@app.function` to it: Modal Function objects are not directly callable, which silently broke all stock B-roll clip fetching until 2026-07-02.

**RTL bidi — RTL embedding per line (2026-07-12)** — mixed Hebrew/English/punctuation (esp. commas) rendered WRONG in libass: the two Hebrew segments around an English word were swapped and commas/`?`/`!` landed on the wrong side, because libass defaults to an LTR paragraph base and a leading RLM (mark) doesn't change it. `_rtl_ass_text` (in `pipeline_core.py`) now wraps EACH `\N` line in an RTL **embedding** `RLE…PDF` (U+202B…U+202C) — forces RTL base so the Unicode Bidi Algorithm resolves exactly like a browser `dir=rtl` element (verified pixel-for-pixel vs Chrome for commas, numbers, `?`/`!`, `ו-CSS`). The hook applies the same wrap per line in `build_caption_ass`. `_fix_rtl_punct` (leading-punct Whisper token-order repair) is unchanged and still runs first. Do NOT revert to the old RLM-prefix/`?!`-insertion approach (it left an LTR base). Tests: `tests/backend/test_rtl_broll.py`.

**B-roll: 2-3s clips at the peak moment (2026-07-12)** — moment duration is clamped to **2-3 seconds** (`broll_fns.py` `_validate`, was 2-5s; Sonnet prompt guidance + examples updated to match). At burn, `_peak_window(clip_path, want_dur)` (`pipeline_fns.py`) picks the highest-MOTION `want_dur` window of the downloaded clip (ffmpeg `fps=8,scale=64,tblend=difference,signalstats` YAVG energy, sliding-window max) and overrides the pre-computed middle window — so the short insert shows the peak action. Best-effort (falls back to `add_clip_window`'s middle on any failure); free (no API). Tests: `tests/backend/test_rtl_broll.py`.

**B-roll cost cap** — stock B-roll is by far the priciest per-video feature (Haiku vision-scores clip frames per moment). `analyze_stock_broll` bounds each job with `_COST_BUDGET` (0.25) and `_MAX_CANDIDATES` (20) in `broll_fns.py` — lowered from 1.00/40 for a ~4× cut. Raising them raises cost per B-roll run; a density cap (1 moment / 8s) also limits moment count.

**Stock search two-prompt split** — `broad_search_prompt` is sent to Pexels/Pixabay (optimized for recall); `strict_eval_prompt` is sent to Haiku vision scoring only (optimized for precision). Never swap them — the stock libraries can't handle the strict prompt and return zero results.

**Mobile upload resilience (design, 2026-07-05)** - chunk POSTs use **XHR, not fetch** (`_postChunkBytes`): fetch reports no upload progress (bar frozen at 0% until a whole 5 MB chunk lands) and has no timeout (a stalled connection hangs forever). XHR gives byte-level `upload.onprogress` (summed across concurrent chunks via `loadedByChunk[]`) and a **stall watchdog** - abort+retry only when NO bytes move for `CHUNK_STALL_MS` (20 s; overridable via `window.__CHUNK_STALL_MS` for tests), so a slow-but-moving upload is never killed, only a truly dead one. Retry policy: a chunk gives up only after 6 network failures **that happen while the page is VISIBLE** - failures coinciding with backgrounding (the OS killing in-flight XHRs) are detected via a `_hiddenEpoch` counter (bumped on every `visibilitychange`-to-hidden; captured before send, compared at failure) and do NOT count, so an upload interrupted by minimizing the browser repeatedly never exhausts its budget. Retries also park on `_whenVisible()` while hidden. `MAX_TOTAL=60` is an absolute backstop. Server 408/429/5xx bounded to 4; everything else (401, etc.) terminal immediately. NOTE: a killed in-flight chunk re-sends fully (no server-side resume), so its progress-bar slice resets - completed chunks stay done. `pollForJSON` likewise treats pure network errors as non-fatal until the deadline. Every chunk reads `slice.arrayBuffer()` BEFORE sending: on Android a gallery-picked file can become unreadable (Google Photos cloud-sync / file changed = ERR_UPLOAD_FILE_CHANGED), which otherwise looks like "Failed to fetch" forever - the explicit read turns it into a terminal "select the file again" error. The error card shows a stage+raw-error detail line and an expandable console log (`consoleLog` ring buffer) for mobile bug reports.

**File byte snapshot at selection (design, 2026-07-09)** — the deeper fix for the Google-Photos-cloud-file problem above. `handleFile` calls `snapshotFile(file)` the moment a file is picked and slices the upload from that stable copy (`chunkedUpload(file, source, onProgress)` — `source` is the snapshot, `file` stays the metadata/resume-signature source). Rationale: a cloud-only file's reference goes stale *during* a long upload (background sync moves it), so lazy per-chunk reads fail partway; copying the bytes ONCE while the reference is still valid immunizes the upload. Two backends by size: `≤ SNAPSHOT_MEM_LIMIT` (150 MB) → in-memory `Blob` from `arrayBuffer()`; larger → IndexedDB (`hebpipe-uploads`/`blobs`, disk-backed/off-heap) put-then-read-back a stable copy. Either read throws on a truly unreadable (never-downloaded cloud) file, and `handleFile` **blocks at selection** with `file.cloud`/`file.cloudTitle` (a real warning telling the user to download to device first) — before any upload or credit spend. `_disposeSnapshot()` frees it on successful upload, on Clear-file, and at the start of the next snapshot; `_idbClearAll()` runs on load to wipe orphans from a prior "start over" reload (a reload can't resume an in-memory File anyway).

**Chunk upload protocol & CORS (2026-07-09)** - chunk POSTs go to a FIXED url `/upload_chunk/` with `key`/`index` in **headers** (`X-Upload-Key`/`X-Upload-Index`), not the query string. A chunk POST always triggers a CORS preflight (Authorization + `application/octet-stream` are non-safelisted); a constant url lets the browser reuse ONE cached preflight (`Access-Control-Max-Age=86400`, set on the OPTIONS response in `app()`) for the whole upload instead of re-flying before every chunk. The backend reads the headers and **falls back to the query string** (`?key=&index=`) so an old-frontend/new-backend deploy window still works, and so `test_api.py` (query-based) still exercises the endpoint. Deploy backend before frontend.

**Chunk upload tuning & resume (2026-07-09)** - `CHUNK_SIZE=1 MB`, `UPLOAD_CONCURRENCY=6`, `CHUNK_STALL_MS=35 s` (history: 5 MB/6 → 2 MB/4 → 1 MB/6). On congested café Wi-Fi (~5 Mbps up) 2 MB chunks each crawled ~20 s and a brief hiccup tripped the 20 s stall watchdog, aborting a live chunk and re-sending the full 2 MB → effective throughput fell to ~½ the link. Smaller 1 MB chunks finish ~2× faster (clearer liveness, less wasted on an abort); the 35 s watchdog only aborts a truly dead socket, never a slow-but-moving one; overhead stays low because all chunks share one cached preflight. **Telemetry**: `chunkedUpload` records `window.__lastUploadStats` (`mb`, `secs`, `mbps` effective, `stalls`, `netRetries`, `serverRetries`, `resentMB`), `console.info`s a summary (captured in the debug ring buffer), and surfaces a line in `#uploadStats` (visible on mobile, no devtools) so a slow upload is measurable (link-bound vs. our churn) instead of guessed. **Resume**: completed chunk indices are saved to `localStorage` keyed by a file signature (`name_size_lastModified`, `UPLOAD_RESUME_TTL=24h` < server's 48h scratch prune); `chunkedUpload` reuses the saved upload key and skips already-sent chunks, so a "try again" (same File) or reload+re-pick resumes instead of restarting. Cleared on full success. A `#uploadNote` ("keep the window open while uploading; you can switch away once processing starts") shows during the upload phase only - uploads run on the device via JS and CANNOT progress while the tab is backgrounded (the OS freezes it); processing/burn are server-side and survive backgrounding.

**Chunk streaming** — `upload_chunk` writes each chunk to a separate Volume file. `process_video` reassembles them with `shutil.copyfileobj` directly to the tempdir, one chunk at a time. This keeps RAM usage flat regardless of video size.

**R2 direct upload — the fast web path (2026-08-06)** — chunk POSTs to the Modal ingress are capped at ~3-4 Mbps regardless of client settings: the browser coalesces every concurrent request onto ONE HTTP/2 connection (per-origin), and the h2 upload flow-control window on the ~120 ms path to us-east-1 is the ceiling (measured; HTTP/1.1 single-conn 5.3 Mbps, 6 real TCP conns 10+ Mbps, same uplink to R2 21 Mbps = uplink-bound). The R2 S3 endpoint speaks HTTP/1.1 only, so parallel XHRs get REAL parallel connections. Flow: `POST /upload_r2/init/` (authed; body `{key,size}`) creates a multipart upload on the backup bucket (object `uploads/u{uid}__{key}.src` — uid-namespaced) and returns presigned part URLs (8 MB parts, 4 h TTL); the browser PUTs parts straight to R2 (no auth header — signature in URL; `r2Upload` in `app.js` reuses the chunked path's stall-watchdog/visibility/retry machinery and resumes via localStorage `<sig>_r2` with saved part ETags, TTL 3 h); `POST /upload_r2/complete/` assembles the object, streams it onto the volume as `chunk_0000` (staging + atomic replace — the exact `/upload_stream` shape, so processing/pending-spawn/retention/reload-resume are untouched), deletes the R2 object, and spawns a registered deferred job. `/complete` is IDEMPOTENT (existing `chunk_0000` short-circuits) so the client retries it safely. The deferred registration keeps the CHUNKED `total_chunks` count — one landed file never trips `_pending_complete` early; `/complete` is the only spawner on this path. **Fallback is load-bearing**: any R2-specific failure (init non-OK, part PUT dead while no part ever succeeded = bucket CORS unset, unreadable ETag = CORS missing `ExposeHeaders`) throws with `r2Fallback` and the caller runs the classic `chunkedUpload` with the SAME key — deploys are safe with zero R2 config. `_probeUplinkMbps` probes the R2 path first (`GET /upload_r2/probe/` → presigned PUT+DELETE pairs; plain fetch, never `apiFetch` — telemetry must not tear down a session) and falls back to the Modal probe. Start Over calls `_r2AbortActive()` (keepalive) before reloading. `api()` mounts the `hebpipe-backup` secret; missing creds → 503 `r2_unavailable` → fallback. **Native Android rides R2 too (2026-08-06, no APK change)**: `nativeUpload` first asks init for `single: true` — ONE presigned PUT for the whole file (the foreground service can't slice parts; the shipped plugin already does binary PUT, so only the target URL changes — and headers MUST be `{}` in R2 mode: the presigned URL is the auth). Single-conn HTTP/1.1 to R2 measured 15.4 Mbps vs ~3-4 through the Modal h2 ingress. An S3 PUT is atomic (object exists == whole file arrived); on the `completed` event the app POSTs `/upload_r2/complete/` `{key, single:true}` (head_object instead of multipart assemble). Close-and-forget is preserved by **`sweep_r2_uploads`** (scheduled every 5 min): for each pending registration ≥60s old with no `chunk_0000` on the volume, it heads `uploads/<full_key>.src` and if present lands it (`_r2_land_on_volume`, shared with the route) and spawns via **`_spawn_pending_job_impl`** — the old `_spawn_pending_job` closure body extracted to module level; the request-path delegate passes `expect_uid=uid` (registrant check), the sweep passes None (it acts on the registration record itself). Reconcile in R2 mode calls `/upload_r2/complete` instead of the `upload_check` byte probe (no chunk files ever land, the probe reads 0 forever); a complete that keeps failing falls into a ~7-min `process_pending` wait for the sweep (`r2NoFallback` — the bytes are in R2, re-uploading is wrong). Any pre-PUT R2 failure falls back to `/upload_stream` (same key; registration `total_chunks=1` fits both). `_cancelActiveNativeUpload` also fires `/upload_r2/abort` (keepalive). **Parallel native uploads (2026-08-06, needs the NEXT Android binary)**: the custom `ParallelUploader` Capacitor plugin (`ParallelUploaderPlugin.java` + `ParallelUploadService.java`) runs N=5 concurrent byte-range PUTs to presigned part URLs inside its own foreground service (single connection ≈ 9 Mbps in the field vs ~20 web) and then completes the multipart DIRECTLY against R2 via a presigned `complete_multipart_upload` URL (init `parallel: true` returns `urls` + `complete_url` + `abort_url`; the XML body is unsigned so any HTTP client can POST it) — the assembled object exists even if the app dies, so the sweep recovers it; the JS `completed` handler still calls `/upload_r2/complete` `{single:true}` as the fast path (works because the object exists). The plugin mirrors the stock uploader's event contract (`{name,id,eventId,payload}`, persisted terminal events + `acknowledgeEvent`) so `_nativeUploadRun` drives both via a `mode` param; preference order: ParallelUploader → single-PUT stock → `/upload_stream`. `_rememberActiveNativeUpload` stores WHICH plugin so Start Over cancels the right one. `MainActivity.onDestroy`'s `stopAllUploads` deliberately does NOT stop this service (sweep makes finish-after-swipe-away correct). S3 quirk handled: CompleteMultipartUpload can answer 200 with an `<Error>` body — the service verifies the body. Tests: parallel cases in `native_upload.spec.js`, `test_parallel_mode_presigns_complete_and_abort` in `test_asgi.py`. **Bucket prerequisites (one-time, needs an Admin R&W R2 token — the object-level backup token gets AccessDenied): run `modal run scripts/r2_bucket_setup.py`** to set CORS (allow PUT+DELETE from the app origin, EXPOSE `ETag` — without it every part "succeeds" but the multipart can never complete) and a 2-day lifecycle expiry on `uploads/` (orphan sweep; the happy path deletes eagerly). **Silence cutter: noise + filler rejection (2026-07-10)** — the cutter's job is to keep ONLY confident real speech; ambient noise (birds, traffic, wind) that Whisper hallucinates words over, and vocalized hesitations ("umm"/"אה"), are cut. Layered in `pipeline_fns.py`: (1) **VAD** threshold `0.5` (Silero, tuned for human voice — non-voice scores low; was `0.35`); (2) `transcribe` sets **`condition_on_previous_text=False`** (the #1 anti-hallucination lever — stops the model "talking through" noise; the Sonnet proofread restores cross-sentence coherence) plus `no_speech_threshold`/`log_prob_threshold`/`compression_ratio_threshold`; (3) **`_segments` noise gate** drops a whole Whisper segment when `no_speech_prob ≥ 0.85`, or `≥ 0.60` with `avg_logprob ≤ -1.0` (the classic hallucination combo) — its audio becomes a cut; (4) **`_is_filler`** flags hesitations (curated Hebrew+English set + tripled-letter elongation regex; deliberately EXCLUDES real words אם/הם/עם/אמא/מאה — Hebrew hesitation "אמ" uses a medial mem, distinct from the final-mem word אם), and words with `prob < 0.15` (very low bar so quiet/fast real words aren't clipped). `compute_keep_segments` now works on the FLAT word stream: silence gaps ≥ `min_sil` cut, and a `filler` word forces a TIGHT cut around its span (`EDGE=0.06`) so the "umm" audio is excised, not just hidden. **(5) VAD word-timestamp repair (2026-07-10):** the cutter is speech-driven (Whisper word gaps), but Whisper routinely INFLATES a word's span to swallow a pause — classically a trailing function word like "אם" reported [16.8,18.14] when the voice is only [18.0,18.14] and 16.8-18.0 is a room-tone pause; energy detection can't catch it (room tone ~-30dB ≈ the clip's quiet-speech level). `_repair_word_timestamps_with_vad` runs faster-whisper's bundled Silero VAD (`faster_whisper.vad.get_speech_timestamps`, voice-presence not loudness) on `clean_wav` and clamps each word to its overlapping voice region via `_clamp_word_to_speech` (leading/trailing trim only; leaves a word untouched if VAD found no overlapping voice, so quiet real words aren't destroyed). This re-exposes the hidden gap → the existing word-gap cutter cuts it, and caption timing gets accurate too. Best-effort (import/run failure keeps raw timings). Verified on the real "bad-silence-cut" clip: 9 long (≥1s) pauses → 0, text stays coherent. Fillers are also skipped in `generate_ass` so captions stay clean even when silence-cut is off. Safety: if NO confident speech survives, the whole clip is kept (never nuke everything). Tuning knobs are module constants (`_NO_SPEECH_*`, `_AVG_LOGPROB_MIN`, `_WORD_PROB_MIN`, `_FILLER_EXACT`). Tests: `tests/backend/test_silence_cutter.py`.

**Key validation pattern** — `_SAFE_KEY_RE` and `_SAFE_DOWNLOAD_KEY_RE` at module level validate upload keys and download keys before any filesystem access. Keys must be `[a-zA-Z0-9_\-]` (plus `.` for downloads), max 128 chars.

**Quota is race-proof via unique keys** — the `videos_used` counter on the user record is display-only; the authoritative consumed-credit count is `_count_quota_used(quota_store, uid)`, a scan of unique `{uid}:{call_id}` keys in the `hebpipe-quota` Dict written one-per-spawn. This avoids the lost-update race a mutable counter has under concurrent `/process` calls (modal.Dict has no atomic incr/CAS). The gate uses `max(record_used, scan_count)` so the record is a floor (existing usage survives migration). Overshoot is bounded to genuine concurrency, never unlimited.
